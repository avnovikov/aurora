# Accessibility findings: Progress, session working set, Settings

result: fail (0 blockers, 8 majors, 4 minors). WCAG 2.2 AA. No proof was run for this job, so contrast is computed here from DESIGN.md hex values (table at the end).

Keyboard walk done in source order for Settings (tabs, fields, chips), the session bar and Progress (Progress has no controls beyond the empty state).

## Findings (most severe first)

1. [major] 2.4.3 Focus Order / 4.1.2. `src/ui/jointHistoryEditor.ts`, `paint()`. Every chip click (joint, side, kind) calls `container.innerHTML = ...`, destroying the focused button. Focus falls to `<body>` and a keyboard or TalkBack user restarts from the top of the page after each choice. Fix: do not rebuild the chip rows. Use `setChipPressed` on the clicked chip (as `wireGear` already does) and re-render only the `.hj-detail` blocks. Or, minimum, record the focused `data-hj*` value before `paint()` and call `.focus()` on the matching new button after. Also label the groups: in `detailHtml` wrap the side row in `<div class="row wrap" role="group" aria-label="${JOINT_LABEL[joint]} side">` and the kind row in `role="group" aria-label="${JOINT_LABEL[joint]} injury type"`. At present "left" and "Surgery" are announced with no joint (1.3.1).

2. [major] 4.1.2 / 2.5.3 / 4.1.3. `src/ui/sessionChalk.ts` `repsStepperHtml` and `src/ui/sessionWeightControls.ts`. The stepper buttons are named only "−" and "+", so every one reads as "minus" or "plus" with no object. The dose figure (`.reps`, `.load-edit`) changes silently when pressed. Fix: `aria-label="Fewer reps"` and `aria-label="More reps"` on `[data-reps-minus/plus]`; `aria-label="Less added weight"` and `aria-label="More added weight"` on `[data-load-minus/plus]`. Add `role="status"` (polite) to the `<span class="reps">` / `.reps-edit` / `.load-edit` wrapper so the new value is spoken. Keep the `−` glyph `aria-hidden="true"` if you add visible text. After tapping "Add weight · 16 kg" the button is replaced by the stepper, so move focus to `[data-load-plus]` after the repaint.

3. [major] 3.3.1 Error Identification / 3.3.3 / 1.3.1 / 4.1.3. `src/ui/settingsView.ts` `wireNumber` and `src/ui/settingsPage.ts` `numberFieldHtml`. The error ("Enter a weight from 0.5 to 100 kg.") is written into a plain `<p class="hint">`: nothing announces it, and the input is not linked to it, so a screen reader user hears nothing after typing 0. `aria-invalid` is set, but the hint is never exposed as the field's description (the usage hint is not either). Fix: in `numberFieldHtml` give the hint `id="${attr}-hint"` and the input `aria-describedby="${attr}-hint"`. In the invalid branch set `hint.setAttribute("role","alert")` (remove it again when valid), or give the hint `aria-live="assertive"` in the markup. Also add `max` for bodyweight, and style `.field input[aria-invalid="true"] { border-color: var(--alert); }` so the field itself, not only the text below it, shows the error state.

4. [major] 1.4.11 Non-text Contrast. `src/style.css` `.field input[type="number"]` uses `border: 1px solid var(--edge)`. `edge` is decorative and 1.3 to 1.9:1 against background and surface in all six palettes (table). The two number inputs are near invisible, which the settings renders confirm. DESIGN.md requires `controlEdge` (3.1:1 or better on both, in every palette) for control borders. Fix: `border: 1px solid var(--control-edge);`. Same token for the focus state below.

5. [major] 1.4.3 Contrast (Minimum). `src/style.css` `.exercise-next-label` (the NEXT / THEN / BEYOND words on Progress) uses `var(--muted-dim)`, a 60% mix of muted into background. At 11.2px it fails in all six palettes: Rassvet 3.17:1 on background (about 3.0:1 on the tinted card), Alvorada 2.58, Ushas 2.62, Revontulet 3.01, Fajr 3.60, Eos 2.65. It is also below the 12px floor in DESIGN.md. The brief's change raised the path chips to muted but missed this label; `muted-dim` has no other use, so drop the token. Fix: `color: var(--muted); font-size: 0.75rem;`.

6. [major] 2.4.11 Focus Not Obscured (and 1.4.10 Reflow). `src/styles/session.css` `html:has(.shell.session) { scroll-padding-bottom: 96px; }`. The bar now holds Log set (52px), the pulse row (about 48px) and 32px padding, so it measures about 141px in the render (more when `session-bar-status` shows). A focused "Why this dose" summary or Steps control scrolled to the bottom edge can sit under the bar. Fix: `scroll-padding-bottom: 176px;`, or measure it: set `--session-bar-h` from `ResizeObserver` and use `scroll-padding-bottom: calc(var(--session-bar-h) + 16px)`. At 200% text size the three-button row has no wrap and `.cta` shrinks; add `.session-bar .work-actions { flex-wrap: wrap; }` and `@media (max-height: 480px) { .session-bar { position: static; } }` so landscape and large-text users do not lose most of the viewport to the bar.

7. [major] 2.4.3 / 4.1.2 (tab pattern). `src/ui/settingsView.ts` `wireTabs`, `src/ui/settingsPage.ts` `tabBarHtml`. The role, aria-selected, roving tabindex, aria-controls and aria-labelledby wiring is correct, and ArrowLeft/ArrowRight wrap. Two gaps. (a) A click, tap, Enter or Space on a tab calls `paint()`, which replaces the whole root and drops focus to `<body>`; only the arrow path restores focus (`focus = true`). TalkBack double-tap and keyboard Enter both lose their place. (b) No Home/End. Fix: in `select`, always re-focus the selected tab after `paint()` (drop the `focus` flag, or pass `true` from the click handler); add `Home: 0` and `End: tabs.length - 1` to the key map. Also give `#settings-panel` `tabindex="0"` so Tab always lands in the panel, and use `hidden` on the three inactive panels if you ever render all four.

8. [major, brief requires 44px; AA 2.5.8 passes at 24px] 2.5.8 / 2.5.5. `src/ui/settingsPage.ts` `trainingHtml`. "Deload week" and "Mute coach voice" are native checkboxes in `label.field.row`. No size CSS exists, so the control is about 13px and the label row about 24px tall, well short of the 44px the brief demands, with only the 0.75rem margin between them. Fix: `.settings .field.row { align-items: center; gap: 0.75rem; min-height: 44px; } .settings .field.row input[type="checkbox"] { width: 1.5rem; height: 1.5rem; flex: none; }`. Or reuse `toggleHtml` (`data-kind="toggle"`, 48px) so the two switches match the chips.

9. [minor] 1.3.1 Info and Relationships / 2.4.6. Settings and Progress. In the settings panels, "Equipment you have", "Your weight", "Past joint injuries", "Palette", "Backup" are `<p class="eyebrow">`, so a screen reader heading list shows only "Your setup". Fix: change them to `<h2 class="eyebrow">` (keep the class so the look does not change; reset `margin`/`font-size` as needed), and give the `<section id="settings-panel">` the existing tab as its name (already there). On Progress, name each `<section class="chain-card">` with `aria-labelledby` pointing at its `h2` (add `id`). Copy: "Your weight" over "Weight you own (kg)" sits next to "Bodyweight (kg)" on the other tab; use the heading "Added weight" and label "Weight you add (kg)" so the two numbers are not confused (3.3.2).

10. [minor] 4.1.3 Status Messages. `src/ui/settingsView.ts` `commit`, `src/ui/settingsPage.ts`. The `role="status"` node exists, which is right, but it is replaced on a tab change and after the first "Saved." an identical string is not re-announced (many screen readers ignore an unchanged live text). It also never clears, so a stale "Saved." sits under the tabs. Fix: in `commit`, set `status.textContent = ""` then, in `requestAnimationFrame` or `setTimeout(…, 50)`, set the message; clear it after about 4 seconds. Name the change where it is cheap ("Equipment saved.", "Palette saved.") so the announcement carries meaning, not just "Saved."

11. [minor] 1.4.1 Use of Colour / 4.1.2. `src/ui/progressView.ts` `pathPreviewHtml`, `activeBlockHtml`. (a) Where you are on the path (start, now, target) is shown by border and text colour only (`.path-step.path-now`), with bold on the target; the list items expose no state. The same fact is repeated in the block below, which limits the harm. Fix: append `<span class="visually-hidden"> (${marker label})</span>` inside each `<li>`, and for the target and current marker add a visible non-colour cue (bold or a leading `✓`/`→`). (b) `aria-current="step"` on `<p class="exercise-current">` is not valid usage outside a list of steps; remove it and rely on the text, or move it to the matching `<li>` in the path `<ol>`.

12. [minor] 4.1.3 / 1.3.1 / 1.1.1. `src/ui/sessionChalk.ts` `pulseBarHtml`, `src/style.css` chip `::before`. (a) `<p class="pulse-chip" role="status">Pulse 112</p>`: if the BPM is updated in place each second, a polite live region speaks every change. Fix: drop `role="status"` from the bpm number and announce only connection changes through `[data-pulse-status]` (`role="status"` there). "Pulse —" is read as "Pulse dash": use `Pulse ${bpm ?? "not connected"}`, or `aria-label`. (b) The decorative `✓` in `button[aria-pressed="true"]:not([data-kind="toggle"])::before` is announced as "check mark" beside "pressed". Fix: `content: "✓" / "";` (alt text syntax, with a plain `content: "✓"` fallback line above it). (c) The session rail marks "done" by lightness alone; add the state word to each notch's visually-hidden title (`Done`, `Now`, `To do`).

## Checked and fine

- Document language is `en-GB`; one `<h1>` per view; Progress cards go h1 then h2 in order.
- Settings tab pattern wiring (roles, `aria-selected`, roving `tabindex`, `aria-controls`/`aria-labelledby`, arrow keys with wrap) is correct apart from items 7a and 7b.
- Touch targets: tabs 48px, palette chips 48px, steppers 48x48, Log set 52px, Failed/Skip/Add weight 44px, Strap summary 44px, equipment and joint chips about 44px (render shows 45px). Only the checkboxes fail (item 8).
- Selection is not colour-only on chips (check mark, filled background, `aria-pressed`).
- Motion: no CSS transitions or animations found; the swipe (`src/ui/sessionSwipe.ts`) honours `prefers-reduced-motion` and Log set is a button alternative to the swipe (2.5.1).
- Session focus ring is a 2px `--foreground` outline with 2px offset (strong in all palettes). Settings and Progress rely on the browser default ring; add one shared rule for consistency: `:focus-visible { outline: 2px solid var(--foreground); outline-offset: 2px; }` (foreground is 6.6:1 or better on every background and surface).
